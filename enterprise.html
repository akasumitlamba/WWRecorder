Media stays with your organization

Recording, screenshots, annotation and editing run on the user’s Windows device. WWRecorder has no account requirement, capture-upload service, advertising SDK or usage-analytics service. It does not send screen content, audio or Keycast input to the developer.

Captures are ordinary PNG and MKV files in the chosen output folder. Apply your Windows permissions, disk encryption, retention and data-loss-prevention policies to completed captures and recovery media. WWRecorder does not encrypt those files itself. Network shares and synchronized folders follow your organization’s and storage provider’s policies.

Clipboard copying, manual sharing and drag-and-drop can send content to another application. Windows clipboard history, sync and remote-desktop redirection require their own endpoint policies.

Administrator controls

Both EXE and MSIX editions read the same optional machine policy. Administrators can deploy DWORD values under the 64-bit registry key:

HKEY_LOCAL_MACHINE\SOFTWARE\Policies\WWRecorder
Policy valueWhen set to 1
DisableKeycastBlocks Keycast activation and checks the restriction before starting its input listeners.
DisableAutomaticClipboardStops automatic copying after captures and player-frame screenshots. Manual Copy remains available as an explicit user action.

Deploy through your approved device-management or registry mechanism, protect the key from ordinary-user writes, and restart WWRecorder. An absent value or DWORD 0 leaves the normal user-controlled behavior available. These are application controls; use endpoint DLP and clipboard policy for organization-wide restrictions.

Clear disclosure before Keycast

Keycast can display recent keys, shortcut combinations, mouse clicks and scrolling inside the recorded area. Before activation, users see a warning that passwords, private text and typing outside the selected recording area may be visible in the recording. They can cancel or enable it and choose whether to remember the acknowledgement.

The warning concerns what viewers may see in the video. WWRecorder does not send this input to the developer and does not create a separate typing-history file. Keycast does not automatically detect or mask passwords. Organizations handling sensitive input can disable it with machine policy.

Media components and integrity checks

Version 1.7.1 includes standalone FFmpeg 9.0.2 for recording/export and Qt 6.12.0 with independent FFmpeg 9.0.1 libraries for playback. Both media paths include the patch for CVE-2026-8461. Updating the standalone encoder alone would not cover the playback libraries.

Build checks verify the approved native component hashes, locked Python dependencies, frozen application startup and actual export/decoder behavior. Dependency advisory checks run before packaging. Builds generate component and payload inventories with SHA-256 hashes. Published installer checksums let IT verify the exact downloaded file.

The EXE updater accepts official GitHub release assets over HTTPS, checks their expected size and SHA-256, and rechecks the staged file before launch. These checks provide download integrity; they do not replace publisher signing or a security assessment. Keep Windows and WWRecorder current and assess files from untrusted sources under your normal media-handling policy.

Deployment and publisher trust

EXE and full-trust MSIX use the same application features, defaults and core payload. Run WWRecorder as a standard user; capture features do not require launching the app as administrator. Full-trust MSIX is not an AppContainer sandbox.

For managed deployment, use the production Microsoft Store product after verifying its available version and publisher under your approval process. The direct-download EXE is unsigned. Microsoft signs the package distributed through its Store. A GitHub release does not mean the same version has reached Microsoft Store. Check the version available through your approved Store channel.

The EXE uses official GitHub release checks and installer delivery. MSIX uses Microsoft Store updates and never queries or launches the EXE updater. Startup uses the edition’s Windows integration and respects Windows restrictions. Settings are separate per edition after first-use import.

Recovery, diagnostics and retention

Recordings finish as saved, explicitly discarded or recoverable temporary media. Failed finalization retains recovery data rather than silently deleting the only playable copy. Export and worker shutdown have time bounds and report failures; closing a processing notice does not cancel the job.

Recovery media is stored in .wwr_temp on the selected output drive. Eligible recorder temporary files older than seven days can be cleaned from known locations; this does not scan every historical folder or securely erase SSDs, backups or cloud copies. Finished captures remain until deleted or removed by storage policy.

EXE settings/logs use %APPDATA%\WWRecorder; MSIX uses package-private LocalState storage. Application logs rotate at 2 MiB with three backups. Native crash logs rotate on the next launch at 2 MiB with one backup. Diagnostic paths and error context may identify users or files. Restrict access and review logs before sharing them.

Support for your security review

Public source, tests, build definitions, dependency locks, media component pins and release checksums are available for inspection. Automated validation for this build passed 1,177 Windows tests and 999 portable tests. Offscreen checks do not replace installed-device acceptance, physical microphone checks or your organization’s approval process.

Evaluate deployment trust, permissions, clipboard/DLP, proxy or denied-egress behavior, recovery handling and your chosen media destinations before broad rollout. These documented controls support that assessment; they are not a claim of ISO, SOC 2 or other independent certification.
