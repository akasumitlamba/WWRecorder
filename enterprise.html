Media stays on the PC

Recording, screenshots, annotation and editing run on the user’s Windows device. WWRecorder has no account, no capture-upload service, no advertising SDK and no usage-analytics service. It does not send screen content, audio or Keycast input to the developer.

The application does not listen for a network command to start a recording. Capture starts from the local dock, the tray menu, or the configured shortcut on that PC. The recording controls are shown on screen while a recording is in progress.

Captures are ordinary PNG and MKV files in the folder the user selects. The default folder is %USERPROFILE%\Videos\WWRecorder. WWRecorder does not encrypt those files. Windows permissions, disk encryption, retention and data-loss prevention apply to them, including copies on a network share or a synced folder.

System sound and microphone recording are off until the user turns a source on. There is no machine policy to force the microphone off or to lock the output folder.

Clipboard copying, manual sharing and drag-and-drop can send a capture to another application. Windows clipboard history, cloud clipboard sync and remote-desktop redirection are Windows features and need their own controls.

Recent Files does not wait for Play. When a video row is loaded, the app runs the bundled ffmpeg.exe on that file to read its duration and one JPEG frame. A video placed in the output folder, including by sync, can be decoded at that moment. On version 1.7.1 that program is FFmpeg 9.0.2. Playing a file in the built-in player uses Qt’s FFmpeg 9.0.1 libraries instead. Both are described under Media security.

Install and uninstall

The standalone installer is Inno Setup. The script asks for the lowest privilege, so a normal install does not request administrator rights. The wizard can also offer an all-users install (PrivilegesRequiredOverridesAllowed=dialog). The default directory is {autopf}\WWRecorder: under the user profile for a per-user install, and under Program Files for an elevated all-users install.

Standard Inno Setup parameters are available because the script does not disable them: /SILENT, /VERYSILENT, /NORESTART, /CURRENTUSER, /ALLUSERS, /DIR= and /LOG=. /ALLUSERS needs elevation. A silent install does not launch the app. Setup stops, including when silent, if WWRecorder is already running. It does not close the app by force.

There is no MSI. [PLACEHOLDER: result of deploying the EXE under the SYSTEM account with Intune or SCCM]. A SYSTEM install is not the same as installing into the signed-in user’s profile, because the script’s default directory and the InstallPath value follow the account that runs Setup.

Uninstall uses the Inno Setup uninstaller and does not delete recordings. An interactive uninstall can also delete %APPDATA%\WWRecorder, which holds settings and the recordings index. A silent uninstall leaves that folder in place. Uninstall refuses to continue while WWRecorder is running. The Store and MSIX test packages are removed from Windows Settings. Removing the test package does not remove EXE settings or recordings.

Administrator controls

Version 1.7.1, in both the EXE and MSIX editions, reads two optional DWORD values under this 64-bit key. No other policy values are implemented. There is no ADMX template in the repository, and there is no value that disables update checks, locks the output folder, or disables the microphone.

HKEY_LOCAL_MACHINE\SOFTWARE\Policies\WWRecorder
Policy valueWhen set to 1
DisableKeycastThe Keycast control will not turn on. An active Keycast session stops the next time recording starts or pause changes. The app does not poll this value on a timer.
DisableAutomaticClipboardStops automatic copying after captures and player-frame screenshots. Manual Copy remains a separate user action.

A missing value or DWORD 0 leaves the user’s own setting in effect. Protect the key from ordinary-user writes and restart WWRecorder after a change. Use Windows clipboard policy and data-loss prevention for organization-wide restrictions.

"DisableKeycast"=dword:00000001
"DisableAutomaticClipboard"=dword:00000001

Keyboard and mouse capture

Two different listeners exist. Security software may alert on either one because the EXE is unsigned and uses a global input hook.

While WWRecorder is running, it listens for the two configured shortcuts (record and screenshot, Shift + Backspace and Shift + Home unless the user changed them). That listener matches those shortcuts only. It does not write a typing log. It starts at launch, even when Keycast is off.

Keycast is separate and off until the user turns it on during a recording. Turning it on shows a warning: keyboard input can appear in the recording, including typing outside the selected area. The user can cancel or enable it, and can choose to remember that choice. Keycast then listens for keys, mouse buttons and scrolling, draws them on the recording, and keeps that recent activity in memory for the overlay. It does not write a separate typing-history file and it does not send input to the developer. Keycast stops when the user turns it off, when recording pauses or ends, and when recording state is applied again while DisableKeycast is set. It does not detect or mask passwords.

Media security and download verification

WWRecorder 1.7.1 addresses CVE-2026-8461, a flaw in FFmpeg’s MagicYUV decoder. A specially crafted video can crash an application or, in some circumstances, run malicious code when a vulnerable decoder opens it. Read the advisory.

Version 1.7.1 carries two FFmpeg branches on purpose:

  • FFmpeg 9.0.2 is the separate ffmpeg.exe used for recording, export, and the Recent Files duration and thumbnail read. The approved build is recorded in packaging/shared/media-security.json.
  • FFmpeg 9.0.1 is the copy inside Qt 6.12.0, used when the built-in player opens a video. Playback is on 9.0.1 because that is the FFmpeg version in the Qt 6.12.0 package. The same manifest records the MagicYUV fix in FFmpeg tag n9.0.1 (libavcodec/magicyuv.c). 9.0.2 is a later 9.0 build used only for the separate encoder.

Compare WWRecorder_Setup_1.7.1.4.exe with SHA-256 d0c7cf976cd9656c60b9e938e9abc11f72990afd610495b28f845643bea3fdf0 before deployment. The EXE updater reads the file size and SHA-256 from the GitHub release metadata for that same asset, then checks the downloaded file again before launch. A mismatch stops the install. That check catches a truncated or altered download. It does not authenticate the publisher, and it does not protect you if the GitHub release itself is the source of a bad file. No signed checksum or build attestation is published.

Network

The EXE update check is the only HTTPS client in the application. Opening a Help or GitHub link uses the user’s browser and is a separate action. The hostnames below are the ones the updater is allowed to use.

HostnameWhy the EXE contacts it
api.github.comHTTPS GET of /repos/akasumitlamba/WWRecorder/releases/latest at startup, then the release-by-tag metadata that carries the asset size and SHA-256. User-Agent: WWRecorder-Update-Checker.
github.comDownload of /akasumitlamba/WWRecorder/releases/download/… when an update is installed.
release-assets.githubusercontent.comAllowed redirect target for that download.
objects.githubusercontent.comAllowed redirect target for that download.

If those hosts cannot be reached, startup reports that the update server could not be contacted. Nothing is installed and existing recordings are not changed. Recording does not require this check. There is no policy to disable it. The website, which users open in a browser, also loads fonts from Google; the application does not.

AppLocker and WDAC

A publisher allow rule cannot match the standalone EXE, because the file has no Authenticode signature. A hash rule can allow one exact file, and every new build needs a new hash. The practical signed distribution is the Microsoft Store package, which Microsoft signs. The GitHub MSIX test package uses a separate test certificate and is not a substitute for that Store approval.

Compatibility

Supported operating systems in the product requirements are 64-bit Windows 10 version 2004 or later, and Windows 11. The installer does not ship a native ARM64 build. [PLACEHOLDER: tested result on ARM64 Windows, and on VDI, Remote Desktop or Citrix].

More than one monitor is supported, including monitors with different Windows scaling and monitors placed to the left of or above the primary display.

Recovery, diagnostics and retention

If saving fails, WWRecorder keeps the recording in its recovery folder and reports the error. Closing a processing notice lets saving continue in the background.

Recovery files are stored in .wwr_temp on the selected output drive. Recorder temporary files older than seven days can be removed from those known locations. Cleanup does not scan every historical folder and it does not securely erase SSDs, backups or cloud copies. Finished captures remain until someone deletes them.

EXE settings and logs use %APPDATA%\WWRecorder. MSIX settings use that package’s private LocalState folder. Application logs rotate at 2 MiB and keep three backups. Native crash logs rotate on the next launch at 2 MiB and keep one backup. Logs can contain usernames and local paths. Restrict access and review logs before sharing them.
